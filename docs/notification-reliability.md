# 通知偶尔不弹的原因与修复

用户反馈：任务完成时「有时候会通知也会有声音，并不是每次都有」；面板里的「试发系统通知」点了一直提示发送失败。

## 定位到的五个问题

### 1. 自检按钮永远 415

`lib/client.js` 发 `POST /task-notifier/api/test` 时没带 `Content-Type`。宿主路由对非 GET 请求要求
`application/json`（挡跨站简单请求），缺了直接回 415，`fetchJson` 抛错，面板就显示「系统通知发送失败」。
所以这个按钮从发布起就没成功过，也让人无法判断系统通知通道本身是否正常。

修复：写接口统一走 `postJson()`，自检、已读、心跳、兜底通知都补上 JSON 头。

### 2. 同一个会话第二次完成起完全静默

客户端去重用的是「已通知过的会话 id」集合 `notified`，页面重新载入前永不清空。
一个会话会跑很多轮，只有第一轮完成会提醒；之后无论完成多少次都不响、不弹。这是「有时候不工作」最主要的原因。

修复：改成按「已通知到的完成时刻」记录（`notifiedAt`），同一会话的新一轮完成时刻更大，照常提醒。
`watermark` 仍然只负责压掉页面载入前就存在的历史未读。

### 3. 中断 / 报错的结果不会提醒

`api-session/error`（会话级失败、欠费）只把任务标成中断，没有推进 `completedAt`；
而客户端判断「是不是新结果」只看 `completedAt`，这类中断永远排在 watermark 下面，一条通知都发不出。
宿主侧这条路径也没有调用系统通知，页面关着时彻底没有提示。

修复：
- 宿主 `markInterrupted()` 在真正改动任务时补 `completedAt`；
- 客户端用 `completedAt || changeAt` 作为结果时刻，兼容旧版宿主；
- 会话级失败在页面离线时也弹系统通知；
- 宿主按会话加 2 秒去重窗口，避免轮次收尾、状态翻转、会话级失败三条路径各弹一次。

### 4. 浏览器通知构造失败后没有兜底

`notifyBrowser()` 返回 `false`（权限被撤销、构造抛错）时，调用方仍然当它发过了。
现在只有真的构造出通知才算成功，否则把会话 id 交给宿主 `/notify` 强制弹系统通知；多个任务合并成一次请求，
避免撞上 `/notify` 的 800ms 冷却。

### 5. 所有通知共用一个 tag

`tag: "dsh-task-notifier"` 让系统把连续几条通知视为同一条的更新，短时间完成多个任务时横幅会被折叠。
改成按会话区分（`dsh-task-notifier:<sessionId>`）：不同会话各弹各的，同一会话的多次完成互相替换。

顺带修了提示音：页面刚载入时 `AudioContext` 处于 suspended，旧实现直接 `return`，启动后的第一条通知没有声音。
现在先 `resume()` 再排音，并在第一次点击/按键时预先唤醒音频上下文。

## 验证

- `npm test`：新增 `test/client-notify.test.js` 锁住上面几条约束；宿主侧补了「写操作必须带 JSON 头」和
  「会话级失败要写 completedAt、重复上报不重复计时」的用例。
- 无头 Chrome 跑真实预览页：自检按钮返回「已发出系统通知」；模拟同一会话连续完成两次，修复前只弹 1 条，
  修复后弹 2 条且 tag 带会话 id。

## 仍然无法覆盖的部分

macOS 专注模式、系统设置里关掉对应应用的横幅、Script Editor 通知权限被拒，都会让 `osascript` 静默丢弃通知，
进程侧拿不到失败信号。排查时先看面板自检是否返回 ok，再检查「系统设置 → 通知」里 `Script Editor`
（系统通知走 osascript）与 DSH 应用本身是否允许。
